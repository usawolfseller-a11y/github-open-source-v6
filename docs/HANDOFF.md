# HANDOFF — как продолжить разработку

**Кому:** инженеру или модели, впервые открывшей этот репозиторий.
**Дата:** 2 ноября 2026.
**Читать первым.** Здесь всё, что нужно, чтобы понять проект и не наступить
на грабли, на которые уже наступали.

---

## 1. Что это такое в одном абзаце

Автономная система, которая каждый день находит интересные open-source
проекты на GitHub, пишет про них посты и публикует в Telegram-канал
[@GitHub_Open_Source](https://t.me/GitHub_Open_Source). Плюс статьи на
Telegraph и dev.to, кросс-посты в Bluesky / Facebook, ежедневный
AI Brief по новостям и недельный дайджест с опросом. Ноль затрат на
инфраструктуру: всё работает на GitHub Actions, генерация — на бесплатном
тарифе Gemini.

**Это v6 — переписывание с нуля.** Старый бот (v5, репозиторий
`donjon1212322/github-projects-bot`) сейчас в продакшене и продолжает
публиковать 4 поста в день. v6 должен его заменить и **не трогает его**.

## 2. Где мы находимся прямо сейчас

| | Состояние |
|---|---|
| Код | готов: 284 теста, branch-inclusive 65.53 %, mutation 18/18 |
| Публикация | **разрешена владельцем 2026-11-03** («публикацию разрешаю и все запреты снимаю») |
| Канал | тестовый при `PUBLISH_TARGET=test`; `main` — только по трём переменным сразу |
| GitHub Actions в этом репо | `Doctor` / `Publishing pipeline` теперь можно включать |
| Продакшн | запуск после живого acceptance-чека в `RUNBOOK.md` |

Исторически аккаунт `usawolfseller-a11y/github-open-source-v6` считался
тестовым, и workflow были отключены вручную по указанию владельца.
**2026-11-03 это указание отменено:** публикация и включение workflow
разрешены. Сохраняется только target lock: пустой тестовый ID никогда не
подменяется основным каналом, а `main` недоступен без
`APP_ENV=production` + `PUBLISH_TARGET=main` + `TELEGRAM_MAIN_CHANNEL_ID`.
Решение о боевом аккаунте/репозитории остаётся за владельцем.

## 3. Что нужно знать до первой строчки кода

Эти решения принял владелец. Они не обсуждаются и не «улучшаются» без него.

| Правило | Почему именно так |
|---|---|
| **3 поста в день** в Telegram | больше — канал выглядит как лента |
| **Длинный текст, не фото** | фото-подпись ограничена 1024 символами и убивает историю |
| **Карточка сверху как превью** | большой превью-блок, текст под ним |
| **Все картинки на ImgBB** | владелец требует; Telegraph-хостинг только резерв |
| **Карточки 1200×630** | горизонтальные, не квадрат |
| **Заголовки не для разработчиков** | обычный человек должен захотеть открыть |
| **SEO — английский, под Google** | dev.to и Telegraph, не русский |
| **Кросс-пост только лучший пост суток** | Bluesky/Facebook, а Telegraph — на каждый пост |
| **Facebook — через make.com из Google Sheet** | v6 не публикует в Page напрямую |
| **Интересные проекты, а не библиотеки** | агентские скиллы и Claude Code — исключение |
| **Технические названия моделей сохраняются** | вендор + точное имя + версия |
| **Никаких обёрток ссылок и трекинга** | владелец отверг |
| **Копирайт не сухой** | живой язык, не пресс-релиз |
| **Никаких «подтверждения нет»** | бриф может выйти без первоисточника, но без этой пометки |

Полный список и обоснования — в [`OWNER_RULES.md`](OWNER_RULES.md).

```

GitHub Search ─┐    │  GitHub Actions (13 кронов)              │
Hacker News ───┼──> │  collect → enrich → gate → rank → queue  │
Telegram web ──┘    │              ↓                           │
                    │  publish_slot (3 раза в день)            │
                    │     ↓ один вызов Gemini на проект        │
```

### Поток генерации (самое неочевидное)

Один проект = **два вызова Gemini**, не десять. Это измеренное решение.

1. **Основной вызов** — бриф: заголовок, факты, статья для Telegraph.
2. **Вызов поверхностей** — 12 полей: отдельные заголовки и тела для
   Bluesky, Facebook, dev.to, плюс `seo_query` и `telegraph_angle`.

Почему не отдельный вызов на каждую площадку: пять независимых писателей,
читающих один README, расходятся в фактах. Проверено: два независимых
вызова дали идентичные технические утверждения — именно потому, что бриф
общий.

**Стоимость:** 8 296 токенов на пост, ~24 888 в день при трёх постах,
27 запросов в день из 1000 доступных.

## 5. Команды

```bash
ghos-v6 doctor              # 13 проверок интеграций, ничего не меняет
ghos-v6 collect             # собрать кандидатов
ghos-v6 publish --slot X    # опубликовать один проект
ghos-v6 crossposts          # обработать очередь кросс-постов
ghos-v6 article             # статья дня
ghos-v6 news                # AI Brief
ghos-v6 digest              # воскресный топ-5 + опрос
ghos-v6 report              # недельный отчёт владельцу
ghos-v6 metrics             # просмотры постов
ghos-v6 poll-close          # закрыть опрос
ghos-v6 learn               # пересчитать модель ценности
ghos-v6 facebook-handoff    # строка в Google Sheet для make.com
ghos-v6 moderation          # удалить спам из обсуждений
ghos-v6 sources             # показать проверенные источники
ghos-v6 scheduled --schedule "10 7 * * *"   # маршрутизация по крону
```

Запуск локально:

```bash
set -a; . .env.local; set +a      # ОБЯЗАТЕЛЬНО в том же вызове оболочки
PYTHONPATH=src python3 -m ghos_v6.cli doctor
```

очищаются в `http.py::sanitize`.

## 8. Ловушки, на которые уже наступали

Читать обязательно. Каждая из них стоила времени.

| Симптом | Причина | Что делать |
|---|---|---|
| `fatal: 'origin' does not appear to be a git repository` | credential-хелпер пропал | пересоздать `/tmp/gitcred.sh` |
| `KeyError: GEMINI_API_KEY` | `. .env.local` не в том же вызове | `set -a; . .env.local; set +a` одной строкой |
| `Unknown schedule` | крон есть в workflow, нет в `_run_scheduled` | добавить маршрут |
| Правка «не применилась» | `p.write_text(s)` вместо `s.replace(...)` | всегда `s = s.replace(old,new,1)` + `grep` |
| Карточка обрезана посередине слова | общий лимит 400 символов на все поля | у каждого поля свой лимит |
| Тест не перезапустился | `assert old in s` не нашёл строку, файл не записан | проверять вывод скрипта правки |
| Telegram не показывает превью | `application/octet-stream` от GitHub releases | только ImgBB |
| AI Brief молчит | фильтр спонсоров/реакции | см. `docs/AUDIT_2026-11-02.md` |

## 10. Что делать в первую очередь

1. `ghos-v6 doctor` — убедиться, что 13/13 отвечают.
2. Прочитать [`ROADMAP.md`](ROADMAP.md), фазы B–E.
3. **Проверить один живой кросс-пост** — единственная непроверенная система.
   Варианты: опубликовать в Bluesky-аккаунты владельца, либо
   написать тест на реальном API с удалением поста сразу после.
4. Прогнать 5 дней в тестовом канале по 3 поста.
5. Только потом `APP_ENV=production` + `PUBLISH_TARGET=main`.

С 2026-11-03 включение GitHub Actions разрешено владельцем; перед боевым
переключением всё равно пройти живой acceptance-чек из `RUNBOOK.md`.

## 10. Аудит 2026-11-03 (продакшен и 5 лет эксплуатации)

Полный отчёт: [`RELIABILITY_2026-11-03.md`](RELIABILITY_2026-11-03.md).

**Сделано:** Variable `TELEGRAM_MAIN_CHANNEL_ID` создана (была только legacy
`MAIN_TELEGRAM_CHANNEL`, из-за чего `APP_ENV=production` не резолвил канал);
wheel теперь содержит 142 иконки; четверговый крон `50 18 * * 4` выполняет
и `close_poll`, и `learn` (раньше `learn` не запускался никогда); добавлено
компактирование состояния (`seen_repos` TTL 180 дней, полные записи
`published` старше 90 дней → лёгкий индекс, ключи дедупа сохраняются);
новый `Lifecycle guard` следит за размером state, активностью репозитория и
доступностью модели Gemini; CI и все workflow переведены на Python 3.13;
порог покрытия 65 %; документация приведена в соответствие с кодом.

**Не сделано и не делалось без владельца:** `pipeline.yml` и `doctor.yml`
по-прежнему отключены, публикации не запускались, живые кросспосты не
проверялись, ключи не перевыпускались. State в отдельную ветку не вынесен —
это отдельный архитектурный шаг.

**Почему компактирование важно:** у v5 есть `Keep Last 10 Published Posts
Monthly`, поэтому его state маленький и 2802 запуска на GitHub Free не
выжгли квоту. В v6 ротации не было: по оценке state вырос бы до ~103 МиБ
на 5-й год и упёрся в лимит GitHub 100 МБ на файл.
